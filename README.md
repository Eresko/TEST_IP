# Ядро магазина цифровых товаров для геймеров (API & Отказоустойчивость)

Данный проект представляет собой высоконагруженное ядро торговой площадки цифровых товаров (аналог GGSel, Plati). Система спроектирована с учетом жестких требований к консистентности данных под параллельными гонками, обработке сетевых таймаутов от внешних поставщиков и финансовой наблюдаемости.

## Этап 1. Ядро API (средняя сложность, ОБЯЗАТЕЛЬНО)
### Контроллер OrderController 
    Создание заказа и получение заказа, для создания используем Idempotency-Key 
    чтобы отсечь дубли, реализовал через Middleware c блокировкой через Redis(KeyDB)
    для получаения заказа обычный запрос, в перспективе можно использовать блокировку 
    сдвухэтапной проверкой, особенно для списков если будет увеличиваться нагрузка. 
    Это гарантирует минимальное кол-во запросов к БД.
## Этап 2. Exactly-once под гонками (сложная, ОБЯЗАТЕЛЬНО)
### Контроллер PaymentController
    Покупатель оплатил заказ. Эквайринг (банк) присылает вебхук: 
    «Деньги пришли». Система переводит заказ в статус paid. Сама задита от дублей в сервисе 
    при входе запроса лочим Cache::lock("lock:order_payment:{$dto->orderId}", 10) на 10 сек
    далее естественно оборачиваем в транзакцию для целостности данных и сверяем статусы если 
    все ок переводим в статус paid и отправляем в доставку через очереди через комит. 
    Статус всегда 200 иначе экваек пришлет еще один хук а нам этого не нужно.

## Этап 5. Каталог под нагрузкой (сложная, бонус)
    Для каталога под высокой нагрузкой (когда тысячи пользователей одновременно обновляют страницы или пытаются выкупить горячие товары) я заложил двухслойную архитектуру:
### a. Чтение без нагрузки на СУБД (Паттерн Cache-Aside):
    Весь активный каталог товаров, категорий и остатков кэшируется в KeyDB (Redis). 
    При GET-запросах приложение вообще не ходит в PostgreSQL — 
    данные мгновенно отдаются из оперативной памяти. 
    Кэш инвалидируется автоматически при изменении админами или при обнулении остатков.
    Ну это я еще в первом пункте писал
    
### b. Борьба с Race Condition на складе (Оптимизация декремента):
    Главная проблема нагруженного каталога цифровых товаров — «оверселлинг» 
    (когда один ключ продали дважды). 
    Логику списания остатков я реализовал через атомарные операции на уровне СУБД. 
    Вместо классического (и медленного) SELECT -> UPDATE, который блокирует таблицы, 
    используется атомарный апдейт с проверкой:
    UPDATE catalog_stocks SET quantity = quantity - 1 WHERE sku = 'KEY-GTA5' AND quantity > 0;
    Если СУБД возвращает 0 затронутых строк — товар мгновенно считается закончившимся, 
    транзакция откатывается, и клиенту улетает ошибка «Нет в наличии», 
    при этом база данных не страдает от взаимных блокировок (Deadlocks).

### c. Перспектива масштабирования:
    При дальнейшем росте трафика архитектура позволяет легко применить CQRS (разделение чтения и записи):
    направить весь трафик покупателей на Read-only реплики PostgreSQL, 
    а мастер-базу оставить только для оформления заказов и админки. Хотя я уже учел это в конфигурации в 
    laravel это делается в confic->database.php выбираем провайдера например pgsql раз мы ее сейчас используем
    и делаем два поля read и write, а так же добавляем опцию 'sticky' => true сейчас просто я указал одну и 
    туже базу. Ну и плюс нужно сделать на уровне базы реплику и местер

##  1. Инфраструктура и Запуск проекта

### Системные требования
* Docker & Docker Compose
* PHP 8.2+ / Laravel 11
* PostgreSQL (Основная СУБД)
* KeyDB вместо Redis (Распределенные блокировки, кэш, очереди)
* RabbitMQ (Диспетчер асинхронных фоновых задач)

### Быстрый старт
1. Склонируйте репозиторий и перейдите в корень проекта.
2. Скопируйте файл конфигурации окружения:
   ```bash
   cp .env.example .env
   ```
3. Запустите инфраструктуру в Docker:
   ```bash
   docker compose up -d --build
   ```
4. Накатите миграции и наполните базу эталонным датасетом из ТЗ:
   ```bash
   docker compose exec app php artisan migrate:fresh --seed
   ```

### Прогон тестов
Для проверки ядра, Exactly-once логики и конечного автомата запустите тестовый набор:
```bash
docker compose exec app php artisan test
```
